# 디스코드 라이 봇 (바이브 코딩)

## 프로젝트 개요 및 동기
### 배경 및 시작점
약 20~30명 규모의 지인 기반 친목 서버에서, 디스코드 업데이트로 표시되기 시작한 음성 채널 누적 통화 시간을 봇을 통해 유지해 보자는 단순한 필요에 의해 시작함

### 해결 방안
24시간 세션 유지가 가능한 봇을 음성 채널에 상주시켜 서버의 활성화 상태를 시각적으로 유지하는 것을 일차적 목표로 삼음

### 기능 확장 및 사용자 경험 개선
봇을 도입한 김에 유저들이 통화방에 더 오래 머물고 함께 소통하는 시간을 늘릴 수 있도록 기능을 확장
- 게임 유틸리티 : 다 같이 게임을 즐길 떄의 편의성을 높이기 위해 손쉽게 여러 팀으로 인원을 분배할 수 있는 `/팀나누기`와 가위바위보를 대체하여 순서나 벌칙자를 정할 수 있는 `/주사위` 기능을 구현
- 가상 경제 시스템 : 통화방 접속 자체에 흥미를 부여하기 위해 출석, 랜덤박스, 강화 등 재화(포인트) 기반의 콘텐츠를 추가하여 유저들의 자연스러운 채널 체류 시간을 증가하도록 유도

## 인프라 및 배포 환경
- 저전력 홈 서버 구축 : 24시간 서버 가동 시 발생하는 데스크톱의 전력 소비 및 유지 비용 절감을 위해 저전력 미니 PC를 도입.
  이를 통해 경제적인 봇 상시 구동 환경 마련
- Docker 기반 컨테이너 배포 : Linux(Ubuntu) OS 환경에서 Docker를 활용해 Node.js 애플리케이션과 MariaDB를 각각 컨테이너화하여 배포.
  이를 통해 로컬 개발 환경과 운영 환경의 일관성을 확보하고, 시스템의 유지보수성을 높임.
- 효율적인 다중 컨테이너 관리 : 미니 PC를 봇 전용이 아닌 다목적 홈 서버로 활용.
  다수의 Docker 컨테이너 리소스(CPU, RAM)와 구동 상태를 직관적으로 모니터링 하기 위해 CasaOS 대시보드 도입.

## 핵심 기능 요약
### 1. 음성 채널 가용성 유지
- 세션 유지 관리 : 사용자가 음성 채널을 비우더라도 봇이 상주하게 하여, 누적 통화 시간이 초기화되지 않도록 유지하는 기능을 구현
- 동적 입장 제어 : `/입장`, `/퇴장` 명령어를 통해 봇을 제어하며, 관리 권한을 가진 사용자만 봇을 조정할 수 있도록 접근 권한을 설정

### 2. 경제 시스템 및 보상 엔진
- 사용자 활동 기반 포인트(P) 시스템 : 서버 내 체류 및 활동에 따라 재화를 지급하는 경제 모델을 구축
- 음성 채널 체류 보상 : 봇과 동일한 음성 채널에 접속해 있는 유저에게 일정 시간마다 자동으로 포인트를 지급하여, 지속적인 채널 참여와 상호작용을 유도
- 다차원 보상 로직 : `/출석` 시 평일/주말 구분, 연속 출석 일수(5일 단위 보너스), 서버 부스트 여부 등을 복합적으로 계산하여 차등적인 보상을 지급
- 재화 소모 및 콘텐츠 : 획득한 포인트로 `/강화`나 `/랜덤박스` 등 게임적 요소를 즐길 수 있도록 하여 사용자 참여도를 높힘

### 3. 서버 관리 및 커뮤니티 유틸리티
- 전용 채널 환경 최적화 : `/채널지정` 기능을 통해 봇 명령어 사용을 특정 채팅 채널로 제한, 메인 채팅 채널의 가독성을 보존하고 데이터 오염을 방지
- 팀 빌딩 시스템 : `/팀나누기` 또는 `/주사위` 기능을 통해 다수의 인원을 무작위로 분배하는 로직을 구현하여 커뮤니티 활동의 편의성을 제공

## 기능 구현 중 발생한 문제와 해결 과정
### 1. 다중 서버 환경에서 봇 제어 권한 및 오작동 방지
- 문제 : 봇이 여러 서버에서 사용될 때 관리자 권한이 낮게 설정되어 있을 경우,
  악의적이거나 의도치 않은 사용자의 `/퇴장` 명령어에 의해 봇 세션이 종료되는 등 서비스 가용성이 훼손될 위험을 발견
- 해결 : `/입장` 및 `/퇴장` 명령어 실행 시, 처음 봇을 호출한 유저의 ID 또는 해당 서버의 관리자 권한 여부를 검증하는 로직을 추가하여 허가된 사용자만 봇을 제어할 수 있도록 보안을 강화.

- 문제 : 출석 기능 구현 시 한국 표준시(KST)를 맞추기 위해 UTC 기준 `Date` 객체에 단순히 9시간을 더하는 연산을 사용.
  이로 인해 자정(00시)에 출석 상태가 정상적으로 초기화 되지 않는 시간차 논리 오류가 발생함.
- 해결 : 임의로 시간을 더하는 하드코딩 방식을 제거하고, 내장 함수 `toLocaleDateString()`의 타임 보정 기능을 활용하여 정확한 현지 시간대를 기준으로 날짜를 판별하도록 매커니즘을 수정

### 3. 전용 채널 지정을 통한 메인 채팅방 오염 방지
- 문제 : 다양한 가상 경제 명령어(출석, 강화 등)가 추가됨에 따라, 일반 채팅 채널에서 명령어가 무분별하게 사용될 경우 유저 간의 텍스트 소통을 방해하고 가독성을 해치는 문제 예상
- 해결 : 게임 중 즉각적으로 사용해야 하는 `/주사위`, `/팀나누기` 명령어를 제외한 핵심 명령어들은 `/채널지정`을 통해 등록된 전용 채널에서만 동작하도록 접근을 제한하여 쾌적한 커뮤니티 환경을 보장

### 4. 동점자 랭킹 정렬 기준 부재에 따른 DB 스키마 개선
- 문제 : `/랭킹` 명령어를 통해 유저를 레벨 순으로 나열할 때, 동일 레벨 달성자가 여러 명일 경우 누가 먼저 해당 레벨에 도달했는지 변별할 수 없는 시스템적 한계를 인지함.
- 해결 : `users` 테이블 구조를 개선하여 강화에 성공한 날짜와 시간을 기록하는 컬럼을 추가.
  이를 통해 동일한 레벨 그룹 내에서도 먼저 달성한 시점을 기준으로 정확하고 공정한 순위 산정 가능

## 사용자 피드백 반영 및 기능 고도화
### 1. 유저 피드백 기반의 로열티 보상 시스템 구축
- 배경 : 서버 내 실사용자(지인)에게 '서버 부스트 유저를 위한 추가 혜택이 필요하다'는 피드백을 접수함.
- 구현 : `/출석` 명령어 수행 시 유저의 서버 부스트 유지 기간을 확인하는 로직을 추가하고,
  유지 개월 수에 비례하여 보너스 포인트를 차등 지급하도록 개선하여 서버 기여도 및 유저 만족도를 높임.

### 2. 로그 함수를 활용한 밸런싱 및 확률형 시스템 설계
- 배경 : 재화 소모 콘텐츠인 `/강화` 명령어에서, 초반 레벨업은 쉽고 후반으로 갈수록 난이도가 상승하는 자연스러운 게임적 밸런스 설계가 요구됨
- 구현 : 레벨이 높아질수록 강화 성공 확률이 0에 수렵하도록 로그 함수 기반의 수학적 모델을 도입하여 계산함.
  이를 통해 직관적이고 안정적인 확률형 가상 경제 콘텐츠를 완성함.

## DB 구조
### guild_settings
  ```
  +----------------------+-------------+------+-----+---------+-------+  
  | Field                | Type        | Null | Key | Default | Extra |  
  +----------------------+-------------+------+-----+---------+-------+  
  | guild_id             | varchar(20) | NO   | PRI | NULL    |       |  
  | dedicated_channel_id | varchar(20) | YES  |     | NULL    |       |  
  +----------------------+-------------+------+-----+---------+-------+
  ```
- 다중 서버(Guild) 환경 지원 : 하나의 봇이 여러 디스코드 서버에서 독립적으로 동작할 수 있도록 확장성을 고려.
  서버 ID(`guild_id`)를 기준으로 전용 채널 등 각 서버별 고유 설정값을 격리하여 관리.

### users
  ```
  +----------------------+---------------------+------+-----+---------+-------+  
  | Field                | Type                | Null | Key | Default | Extra |  
  +----------------------+---------------------+------+-----+---------+-------+  
  | guild_id             | varchar(20)         | NO   | PRI | NULL    |       |  
  | user_id              | varchar(20)         | NO   | PRI | NULL    |       |  
  | level                | int(10) unsigned    | YES  |     | 1       |       |  
  | failure_count        | int(10) unsigned    | YES  |     | 0       |       |  
  | point                | bigint(20) unsigned | YES  |     | 0       |       |  
  | consecutive_days     | int(10) unsigned    | YES  |     | 0       |       |  
  | last_attendance_date | date                | YES  |     | NULL    |       |  
  | last_level_up_at     | datetime            | YES  |     | NULL    |       |  
  +----------------------+---------------------+------+-----+---------+-------+
  ```
- 복합 키를 활용한 데이터 격리 : 동일한 유저가 여러 서버에 소속될 수 있는 디스코드 생태계의 특성을 반영.
  `guild_id`와 `user_id`를 복합 키로 설정하여, 서버 간 유저의 재화 및 레벨 데이터가 혼선 없이 완벽히 격리되도록 설계

### system_settings
  ```
  +---------------+-------------+------+-----+---------+-------+  
  | Field         | Type        | Null | Key | Default | Extra |  
  +---------------+-------------+------+-----+---------+-------+  
  | setting_key   | varchar(50) | NO   | PRI | NULL    |       |  
  | setting_value | text        | YES  |     | NULL    |       |  
  +---------------+-------------+------+-----+---------+-------+
  ```
- 시스템 상태 유지 및 동적 데이터 관리 : 봇 재부팅(업데이트 등) 시 휘발되는 상태 데이터를 보완하기 위해 구성.
  재가동 시 최신 패치 내역을 전용 채널에 자동 전송하는 등, 코드 내 하드코딩을 방지하고 시스템 환경 변수를 Key-Value 형태로 유연하게 관리
